## 4.1 Testing Objectives and Strategy

The objective of the testing phase for the Intelligent Accommodation Review System (IARS) was to verify that the implemented functionality across the three constituent services — the React client, the Node.js/Express/MongoDB server, and the Python sentiment microservice — behaved correctly against the requirements established during system analysis, and that the three services interoperated correctly as a whole. Because IARS integrates several distinct concerns (authentication, listing management with image verification, booking and payment, review submission with automated sentiment scoring, offline request handling, a recommendation engine, and administrative moderation), the testing strategy was designed to exercise each module both in isolation and as part of the end-to-end guest, owner, and admin workflows described in Chapter 3.

Testing combined black box and white box approaches. Black box testing was used to validate externally observable behaviour — form submissions, HTTP responses, and role-based access restrictions — without reference to how a given controller or component achieved that behaviour internally. White box testing was reserved for logic that carries meaningful branching and is not adequately exercised by input/output checks alone, such as the booking overlap-detection logic, the sentiment service's rule-based negation override, the recommendation engine's section-selection logic, and the image duplicate-hash comparison performed during property image upload.

Testing was organised along two complementary axes. The first axis was by user role: guest-facing flows (registration, search, booking, review, offline requests, recommendations), owner-facing flows (listing creation, image upload, offline request responses), and admin-facing flows (listing approval, image audit, user management) were each tested against the permissions and UI states appropriate to that role. The second axis was by functional module, following the structure already established in the requirements and design chapters, so that every module identified in the use case catalogue had at least one corresponding test case.

All manual test execution was performed against a locally seeded MongoDB instance populated using the seeding scripts under `server/scripts` (`seed.js`, `seedAdmin.js`, `seedProperties.js`, and `seedDemoReviews.js`), which provided a repeatable baseline of users, properties, and reviews for each test run. The Python sentiment microservice was run concurrently so that review submissions during testing exercised the real `/predict` classification pipeline rather than a stub. Stripe payments were tested exclusively in Stripe's test mode using publishable/secret test keys, and no production payment credentials were used at any point during testing.

## 4.2 Black Box Testing

Black box testing treated each module of IARS as a set of inputs and expected observable outputs, without reference to the underlying implementation. For the authentication module, this meant submitting registration and login forms with valid, invalid, and boundary-case data (duplicate emails, incorrect passwords, missing fields) and confirming that the correct HTTP status codes, error messages, and JWT tokens were returned, and that role-based UI elements and route access matched the guest, owner, or admin role encoded in the token.

For the property and search modules, black box testing focused on the relationship between input filters submitted to `GET /api/search` (city, title, price range, and availability date) and the set of properties returned, with particular attention to the rule that only properties with `verificationStatus`/listing status of `approved` are ever surfaced to guests, regardless of the filters applied. Listing creation and image upload were tested by submitting valid and invalid image files (correct and incorrect formats, oversized files, and repeated uploads of an identical file) and observing the resulting `verificationStatus` and error responses, without inspecting how the server computed those outcomes internally.

Booking, payment, cancellation, review, and offline-request flows were similarly tested from the perspective of a user interacting with forms and buttons: submitting a booking for available or already-booked dates, completing a Stripe test-mode checkout, cancelling a confirmed booking, submitting a review against a completed booking, and submitting an offline request with or without an authenticated account. In each case, the test verified that the response returned to the client (success payload, error code, or status change visible on screen) matched what the requirement specified, and that role restrictions were enforced — for example, that only the guest who made a booking can cancel it, and that an admin-only endpoint rejects requests from a guest or owner token. Admin screens (user list, image audit, listing approval) were tested by confirming that the actions available in the UI produced the expected state changes and were unavailable to non-admin sessions.

## 4.3 White Box Testing

White box testing was applied to logic paths where correctness depends on internal branching that black box input/output testing alone cannot adequately probe. The most significant target of white box testing was the booking availability and overlap-checking logic in the booking controller. This logic first checks whether the requesting guest already holds a booking for the same property covering the requested dates, in which case it raises an error tagged `BOOKING_ALREADY_EXISTS`; if not, it separately checks whether the requested date range overlaps any other guest's existing confirmed booking for that property, raising `DATES_UNAVAILABLE` in that case. Because these are two distinct code paths with two distinct error codes reached under different combinations of existing bookings, test cases were designed to walk through each branch individually — an overlap against the tester's own prior booking, an overlap against a different guest's booking, and a genuinely free date range — to confirm each branch was reachable and returned the correct code and `totalAmount` calculation (price × nights).

The sentiment microservice's rule-based negation override was tested with reference to its internal logic path rather than only its final label. The TF-IDF plus Logistic Regression classifier can mis-score short reviews containing a negated positive adjective (for example, "not clean") as positive purely from the presence of the adjective "clean"; the override logic detects negation cue words adjacent to sentiment-bearing terms and flips or dampens the classifier's raw output before the final label and aspect list are returned. Testing here specifically targeted inputs constructed to trigger this override path, rather than only random review text, so that the branch could be confirmed as functioning rather than merely coincidentally correct.

The image duplicate-detection logic was examined at the level of its SHA-256 hashing and comparison path: whether a newly uploaded image's hash matched any hash already stored against the same property or against other properties, and how that comparison interacted with the heuristic `aiScore` computation and the `verificationStatus` transition. Finally, the recommendation engine's section-selection branching — the condition that determines whether a request is served the cold-start set (`top_bayesian`, `best_reviewed`, `trending`) or the personalized set derived from booking, view, and search history — was traced directly against the code path that inspects whether the requesting user has an authenticated session with recorded history, to confirm the boundary between the two modes behaved as designed rather than only observing the rendered output.

## 4.6 Evaluation of AI Components

### 4.6.1 Sentiment Model Evaluation

Evaluating the sentiment microservice's classification quality was treated as an ongoing methodological activity carried out during development rather than a single, isolated benchmarking exercise producing a fixed set of headline figures. Because the underlying classifier is a TF-IDF (1–3 gram) feature representation feeding a Logistic Regression model, its accuracy, precision, and recall on any given evaluation set can in principle be computed against a held-out labelled sample of reviews using standard classification-report tooling; the more informative activity for the purposes of this dissertation, however, was to verify that the pipeline behaved sensibly on inputs representative of what real guests would write, and that the rule-based negation override correctly corrected a known category of classifier error rather than merely existing as unused code.

Testing proceeded by constructing a set of sample reviews spanning clearly positive statements ("The room was spotless and the staff were incredibly helpful"), clearly negative statements ("The room was dirty and the wifi never worked"), and deliberately mixed statements combining a positive element with a negative one ("Great location, but the room was noisy at night"), and confirming that each was returned with the expected `positive`, `negative`, or `mixed` label along with a plausible confidence score and a non-empty aspect list drawn from the nine defined categories (cleanliness, staff, location, room, wifi, value, facilities, food, noise). Particular attention was paid to short reviews built around a negated adjective, such as "The room was not clean" or "Staff were not helpful at all," which a purely lexical bag-of-n-grams model is prone to mis-classify as positive because the sentiment-bearing adjective itself ("clean," "helpful") is positive in isolation. These inputs were used specifically to exercise the rule-based negation override, and it was confirmed that the override correctly recognised the negation cue adjacent to the sentiment term and adjusted the final label to negative rather than allowing the raw classifier output to stand uncorrected.

This qualitative, scenario-driven testing approach does not substitute for a formal accuracy/precision/recall evaluation against a large held-out labelled corpus, and no such large-scale numeric evaluation is claimed here. What it does establish is that the pipeline's two layers — the statistical classifier and the deterministic override — were each exercised against inputs designed to probe their respective responsibilities, and that the override's stated purpose of correcting known negation failure cases was verified to hold on representative examples rather than assumed from its presence in the code.

### 4.6.2 Recommendation Engine Evaluation

The recommendation engine was evaluated by manually constructing a guest account, deliberately generating a history of interactions for that account, and then confirming that the sections and per-property `matchReason` fields returned by `GET /api/recommendations` reflected that history correctly, rather than by comparing against a fixed ground-truth ranking (which does not exist for a personalization feature of this kind). A fresh guest account was created and, in a fresh browser session with no prior activity, was confirmed to receive only the three cold-start sections (`top_bayesian`, `best_reviewed`, `trending`), establishing the baseline anonymous/no-history behaviour described in Chapter 3.

The same account was then used to generate a realistic activity trail: the guest searched for properties in a specific city, viewed several individual property pages within that city, and completed a booking on one of them. After this history had accumulated, the recommendation request was repeated, and it was confirmed that the response transitioned from the cold-start set to the personalized set of up to six sections. Specifically, the `previous_bookings` section was checked to contain the property the guest had actually booked, the `recent_searches` section was checked against the city term the guest had searched, `viewed_similar` was checked to surface properties sharing attributes with the ones the guest had viewed, and `popular_in_city` was checked to surface other well-reviewed properties in the same city the guest had shown interest in. Each returned property's `matchReason` field was inspected to confirm it referenced a signal that was actually present in the guest's recorded history (for instance, referencing the searched city or the booked property) rather than an arbitrary or generic justification.

This manual validation approach confirms that the boundary condition between cold-start and personalized modes is correctly triggered by the presence of history, and that the content of each personalized section is traceable to a real, verifiable signal in that guest's own activity, which was the primary property the recommendation engine needed to demonstrate. It does not constitute a large-scale offline evaluation against held-out interaction logs, which was outside the scope of manual testing performed here.

### 4.6.3 Image Verification Heuristic Evaluation

The image verification module's heuristic `aiScore`, which is derived from image dimension and compression characteristics rather than from a trained fraud-detection or authenticity-classification model, was evaluated by manually assembling a small set of test images spanning genuinely distinct quality tiers: high-resolution, unedited photographs taken directly from a camera or modern smartphone; deliberately downscaled or heavily compressed low-resolution images; and byte-identical duplicates of images already uploaded to a listing (as also exercised in TC-08). Each image was uploaded through the normal listing-creation flow, and the resulting `aiScore` and `verificationStatus` were recorded and compared against the intuitive quality tier the image belonged to.

The high-resolution genuine photographs were consistently assigned higher heuristic scores and reached `pending` (awaiting admin review) rather than being automatically flagged, while the low-resolution and heavily compressed images tended to receive lower scores, consistent with the heuristic's basis in dimension and compression characteristics rather than genuine content analysis. Duplicate images were correctly separated out through the SHA-256 hash comparison path rather than through the `aiScore` itself, since the score alone cannot distinguish a duplicate from a low-quality original.

It is important to state plainly, and consistently with how the feature is described in the system design, that this heuristic is not a trained machine-learning fraud-detection model and was never claimed to be one; it is a deterministic scoring function intended to surface likely candidates for closer inspection, not to make an autonomous accept/reject decision. Consequently, the evaluation performed here was limited to confirming that the score behaved plausibly across a small, hand-selected set of test images rather than measuring detection accuracy against a large adversarial dataset. The image audit screen and the listing-approval gate that requires at least one `verified` image (Section 4.4.19) exist precisely so that an administrator, rather than the heuristic alone, makes the final verification decision, and this human-in-the-loop safeguard was treated as the primary mitigation for the heuristic's inherent limitations throughout testing.

## 4.7 Defects Identified and Resolved During Testing

Several defects were identified during the course of development and testing and were resolved before the workflows described above were considered stable. During early testing of the booking module, it was found that a booking could be created for dates that overlapped an existing confirmed booking on the same property, because the initial implementation of the booking creation logic checked only whether the requesting guest already held a booking on those dates and did not separately check for conflicts against other guests' bookings. This was resolved by introducing the second, distinct overlap-detection branch — now surfaced as the `DATES_UNAVAILABLE` error code alongside the guest-specific `BOOKING_ALREADY_EXISTS` code — so that any overlapping reservation on the property, regardless of which guest holds it, is rejected at creation time.

During testing of the image upload flow, it was found that uploading several images to the same listing in quick succession could, under certain timing conditions, allow two images with identical content to both pass through as `pending` rather than one being flagged as a duplicate, because the duplicate-hash comparison was initially performed only against images already persisted at the start of the request rather than against the full batch being uploaded together. This was resolved by extending the duplicate check to compare hashes within the same upload batch as well as against previously stored images, closing the gap that had allowed within-batch duplicates to slip through undetected, as later confirmed by TC-08.

During testing of the review and sentiment integration, it was found that after a new review was submitted and classified, the property's `sentimentSnapshot` — the aggregated summary shown on the property detail page — did not immediately reflect the new review's sentiment and aspect data, because the snapshot-resync step had not yet been wired into the review-creation controller and instead relied on a separate script being run manually. This was resolved by invoking the resync logic directly at the end of the review-creation flow, so that the snapshot is recalculated synchronously whenever a review is saved, which was subsequently confirmed by TC-13. Finally, it was found during early testing of the admin listing-approval endpoint that a listing could be approved even when none of its images had been marked `verified`, since the image-verification gate had not yet been added to that endpoint; this was resolved by introducing the explicit check for at least one `verified` image before allowing `PUT /api/admin/listings/:id/approve` to proceed, which TC-19 was later designed specifically to confirm.

## 4.8 Chapter Summary

This chapter has presented the testing strategy applied to IARS, combining black box and white box techniques across the client, server, and sentiment microservice, organised by user role and by functional module, and executed manually against a locally seeded MongoDB instance and a live sentiment service. Twenty representative test cases were designed and executed covering authentication, search, listing and image verification, booking and payment, cancellation, review and sentiment classification, offline requests, recommendations, admin approval, and multilingual layout, all of which produced Pass outcomes on the execution run documented here. The evaluation of the system's AI-adjacent components — the sentiment classifier, the recommendation engine, and the image verification heuristic — was conducted through targeted, scenario-based manual validation rather than large-scale statistical benchmarking, and was reported honestly on that basis. Several genuine defects uncovered during development, spanning booking overlap detection, batch-level image deduplication, sentiment snapshot synchronisation, and the listing-approval verification gate, were documented alongside the fixes applied to resolve them. Having established that the implemented system behaves correctly against its stated requirements and that its more experimental components were evaluated appropriately for their nature, the following chapter reflects on the project as a whole, considering what these testing results imply about the system's readiness, the limitations of the evaluation performed, and directions for future work.
