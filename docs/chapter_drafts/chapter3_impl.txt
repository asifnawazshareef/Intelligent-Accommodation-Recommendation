## 3.10 Development Environment and Tools

The implementation of IARS was carried out using a JavaScript-first toolchain on the client and server tiers, complemented by a Python-based scientific computing stack for the sentiment microservice. This separation of environments was a deliberate architectural choice: the MERN application handles all transactional, relational-style logic (users, listings, bookings, offline requests) through Node.js and MongoDB, while the sentiment microservice is isolated as an independently runnable FastAPI application so that its scikit-learn dependencies, model artifacts, and Python runtime do not entangle the Node.js dependency tree. Both halves of the system communicate over a plain HTTP contract, which kept the two codebases loosely coupled throughout development and allowed each to be started, tested, and restarted independently during local development.

On the frontend, the project was scaffolded with Vite rather than Create React App, chosen for its fast cold-start and hot-module-replacement characteristics during iterative UI development. React 18 was used with plain JSX rather than TypeScript, in keeping with the technology constraints set for the project, and Tailwind CSS supplied the utility-first styling layer on top of which shadcn/ui component primitives (housed under `client/src/components/ui/`) were composed into buttons, cards, dialogs, tables, and form controls. Client-side routing was implemented with `react-router-dom` v6, HTTP communication with `axios`, iconography with `lucide-react`, and internationalisation with `i18next` and `react-i18next`.

On the backend, Node.js and Express were used with native ES module syntax (`"type": "module"` in `package.json`), which required consistent use of `import`/`export` syntax throughout the controllers, routes, and utility modules rather than CommonJS `require`. Mongoose was used as the object-document mapper over MongoDB, `bcryptjs` for password hashing, `jsonwebtoken` for stateless authentication tokens, `multer` for handling multipart image uploads, and the Stripe Node SDK (configured in test mode) for payment processing. The sentiment microservice was built with FastAPI served by `uvicorn`, with `scikit-learn` providing the TF-IDF vectoriser and logistic regression classifier, `joblib` for model persistence, and `pandas` for dataset handling during training.

Version control was managed with Git, and the three runtimes (client, server, sentiment service) were run concurrently during development using separate terminal processes, with environment-specific configuration isolated into `.env` files per service so that secrets such as the JWT signing key, MongoDB connection string, and Stripe API keys were never hard-coded into source files. The combination of tools listed in Table 3.18 reflects a stack that is conventional for a MERN-based final year project while still accommodating the specialised requirements of a machine-learning-backed sentiment pipeline and a multilingual, RTL-aware user interface.

## 3.11 Backend Implementation

### 3.11.1 Project Structure and Module Organization

The Express application under `server/` follows a conventional layered organisation that separates configuration, request handling, data modelling, cross-cutting concerns, and reusable computation into distinct directories. Two configuration modules live under `config/`: `db.js`, which establishes the Mongoose connection to MongoDB, and `stripe.js`, which instantiates the Stripe client after validating that the configured secret key is in test mode. Request handling logic is concentrated into eleven controller files under `controllers/` — `authController`, `propertyController`, `bookingController`, `reviewController`, `searchController`, `sentimentController`, `stripePaymentController`, `offlineRequestController`, `listingModerationController`, `imageAuditController`, and `userManagementController` — each of which owns the business logic for one functional area rather than mixing concerns across a single monolithic file. Four middleware modules under `middleware/` supply authentication (`authMiddleware.js`, exporting `protect` and `optionalProtect`), authorisation (`roleMiddleware.js`, exporting `authorize(...roles)`), centralised error handling (`errorMiddleware.js`, exporting `notFound` and `errorHandler`), and file-upload validation (`uploadMiddleware.js`, the multer configuration for property images). Seven Mongoose schemas live under `models/`, and nine route files under `routes/` bind URL paths to controller functions with the appropriate middleware chain applied per endpoint.

A `services/` directory holds `sentimentService.js`, the single point of contact between the Express server and the Python sentiment microservice; it wraps an axios POST request to the `/predict` endpoint with a fifteen-second timeout and a graceful fallback path so that a temporarily unavailable sentiment service does not prevent a review from being saved. The heaviest concentration of domain logic sits in `utils/`, a fourteen-file directory that includes `bayesianRanking.js`, `bookingAmount.js`, `bookingReviewStatus.js`, `buildUserProfile.js`, `collaborativeFiltering.js`, `generateToken.js`, `imageAiScore.js`, `imageVerification.js`, `personalizedRecommendationEngine.js`, `propertySentimentStore.js`, `propertySignals.js`, `propertySimilarity.js`, `recommendationEnrichment.js`, and `sentimentAggregation.js`. Keeping these as independently testable pure-function modules, rather than inlining their logic into controllers, was a conscious structural decision that made the recommendation and sentiment-aggregation pipelines easier to reason about as they grew in complexity. Finally, a `scripts/` directory holds one-off maintenance and data-seeding utilities — `seed.js` (which creates the admin account from `ADMIN_*` environment variables), `seedProperties.js`, `seedDemoReviews.js`, `syncPropertySentiment.js`, `reanalyzeReviews.js`, and `clearListings.js` — which are run directly with Node rather than exposed through the API, since they are development and data-maintenance tools rather than user-facing functionality.

```text
server/
├── config/            (db.js, stripe.js)
├── controllers/        (11 controller files)
├── middleware/          (auth, role, error, upload)
├── models/             (7 Mongoose schemas)
├── routes/             (9 route files)
├── services/           (sentimentService.js)
├── utils/              (14 utility modules)
└── scripts/             (seed and maintenance scripts)
```

This structure keeps each functional module — authentication, property/image handling, booking/payment, review/sentiment, offline requests, recommendations, and administration — reachable through a small, predictable set of files, which in turn made it straightforward to trace a request from its route definition, through its middleware chain, into its controller, and finally into the utility functions and Mongoose models it depends on.

### 3.11.2 Authentication and Authorization Implementation

User authentication in IARS is implemented as a stateless, JWT-based scheme layered on top of a `User` Mongoose model with a `select: false` password field. When a new guest or owner registers, `authController.registerUser` deliberately restricts the accepted `role` value to `guest` or `owner`; there is no code path through which a self-registering user can obtain the `admin` role, since administrator accounts are only ever created out-of-band by running `scripts/seed.js`, which reads `ADMIN_*` environment variables and inserts the account directly into the database. This design decision reflects the principle that privileged accounts should never be reachable through a public-facing endpoint. On successful registration, the controller issues a JSON Web Token, following the RFC 7519 specification [20], by calling `generateToken(user._id)`, a small utility that wraps `jwt.sign({ id }, JWT_SECRET, { expiresIn: JWT_EXPIRES_IN || "7d" })`, giving every issued token both a cryptographic signature and a bounded lifetime that defaults to seven days if no explicit expiry is configured.

Login is handled by `loginUser`, which re-fetches the target user document with `.select("+password")` — necessary because the schema excludes the password field from ordinary queries by default — and then delegates the credential comparison to the `matchPassword` instance method defined on the `User` model, which internally calls `bcrypt.compare` against the stored hash. Password hashing itself happens transparently through a Mongoose `pre("save")` hook on the `User` schema: whenever a document is saved and its `password` field has been modified, the hook salts and hashes the plaintext with bcrypt [21] using ten salt rounds before persistence, and leaves the field untouched on saves that do not touch the password (for example, a profile update). This guarantees that plaintext passwords are never written to the database and that re-saving a user for an unrelated reason cannot accidentally re-hash an already-hashed value.

Authorisation on protected routes is enforced through two complementary middleware functions. `protect`, defined in `authMiddleware.js`, extracts the bearer token from the `Authorization` header, verifies its signature and expiry against `JWT_SECRET`, loads the corresponding user (excluding the password field) into `req.user`, and responds with a 401 status on any failure — a missing header, an invalid signature, an expired token, or a user that no longer exists. `optionalProtect` performs the identical lookup but, critically, does not reject the request when no token is present or the token is invalid; it simply leaves `req.user` undefined and allows the request to continue. This distinction is what allows endpoints such as `/api/search`, `/api/recommendations`, and the property detail endpoint (`GET /api/properties/:id`) to serve both anonymous visitors and authenticated users from the same route, differentiating their response only when an authenticated identity is actually present — for instance, personalising recommendation results for a logged-in guest while still returning a sensible cold-start result set for an anonymous one. Role-based access control is then layered on top of `protect` through `authorize(...roles)`, a higher-order middleware in `roleMiddleware.js` that inspects `req.user.role` (already populated by `protect`) against an allow-list of roles supplied per route and returns a 403 if the authenticated user's role is not among them; because it runs strictly after `protect`, it can assume `req.user` is already a valid, loaded document.

On the client, this scheme is mirrored by `client/src/services/api.js`, which reads the JWT and user object out of `localStorage` and attaches an `Authorization: Bearer <token>` header to every outgoing axios request. A response interceptor watches for any 401 response — excluding the login and register calls themselves, since those legitimately return non-2xx statuses for invalid credentials rather than an expired session — and, upon seeing one, clears the stored session and redirects the browser to `/login?session=expired`, so that a token which has expired or been revoked server-side does not leave the user stranded on a broken authenticated view.

### 3.11.3 Property Management and Image Verification Implementation

Property creation is an owner-only workflow that begins on the client as a multipart form submission containing the listing's `title`, `description`, address fields (`address`, `city`, `country`), `price`, an `availabilityCalendar` serialised as a JSON string, and up to five image files. This payload passes through the `uploadMiddleware.js` multer configuration before it reaches `propertyController.createProperty`, and that configuration enforces both a maximum file count of five and a maximum size of five megabytes per file, restricted to the `jpg`, `png`, and `webp` MIME types — a request that violates either constraint is rejected before any controller logic executes. Inside `createProperty`, each accepted file is passed through `buildVerifiedImagesFromFiles()`, a routine that computes a SHA-256 hash of the file contents to detect duplicate uploads (whether duplicated within the same submission or against images already stored for other properties), and separately computes a heuristic quality score using `server/utils/imageAiScore.js`. That module inspects the raw PNG, JPEG, or WEBP file headers to recover pixel dimensions and estimates a score from resolution, apparent compression artefacts, and aspect ratio; it is explicitly a deterministic heuristic scoring function rather than a trained image-classification model, and this distinction is preserved throughout the codebase and the admin-facing tooling that consumes its output. The resulting image metadata — hash, dimensions, heuristic score, and an initial `verificationStatus` — is attached to the new `Property` document, which is itself created with `status: "pending"`, meaning it is invisible to guest-facing search and browse endpoints until an administrator reviews it.

Editing an existing listing is handled by `updateProperty`, which supports a mixed image update: the client sends a `retainedImageIds` array identifying which of the property's existing images should be kept, alongside any newly uploaded files, which are processed through the same `buildVerifiedImagesFromFiles()` path as on creation. Images that are neither retained nor newly uploaded are dropped from the property's image list, which allows an owner to prune a listing's gallery without needing to re-upload every image on every edit.

The verification status attached to each image — `verified`, `pending`, `suspicious`, or `rejected` — governs what guests are permitted to see. Guest-facing read paths apply `filterGuestImages`, which strips any image that is not `verified` from the response, so a guest browsing an approved listing only ever sees images that have cleared moderation, even if that listing also carries images still pending review or flagged as suspicious from a more recent edit. Owner and administrator views, by contrast, are shown every image except those explicitly `rejected`, since owners need visibility into the state of their own submissions and administrators need the full picture in order to adjudicate it. This split between what an owner submits, what an administrator reviews, and what a guest is ultimately shown forms the backbone of the image-verification workflow that later feeds into the listing-approval gate described in section 3.11.8.

### 3.11.4 Booking and Payment Implementation

The booking workflow is coordinated by `bookingController.createBooking`, which performs a sequence of server-side validations before a `Booking` document is ever written, deliberately duplicating checks that the frontend also performs, on the principle that client-side validation can be bypassed and must never be the only line of defence. The controller first confirms that the target property's `status` is `approved` — a guest cannot book a listing that has not cleared admin moderation — and then calls `isWithinAvailability()` to verify that the requested date range falls inside the property's `availabilityCalendar`. It subsequently checks for date overlap against the property's existing bookings that are in a `pending` or `confirmed` state, returning a distinct `BOOKING_ALREADY_EXISTS` error code when the same guest already holds an active booking for that property and dates, and a `DATES_UNAVAILABLE` code when the conflict is with a different guest's booking, which allows the frontend to present a more specific and useful error message in each case rather than a single generic failure. Once these checks pass, the total price is computed by `calculateBookingTotal`, which multiplies the property's nightly `price` by the number of nights returned by `countBookingNights` over the requested check-in and check-out dates.

Payment is handled through Stripe in test mode via `stripePaymentController.createCheckoutSession`, which constructs a Stripe Checkout Session configured for card-only, one-time `"payment"` mode. Because Stripe Checkout for this integration operates in US dollars while the platform's listing prices and totals are denominated in PKR, the controller converts the booking's `totalAmount` to USD cents using `toStripeUsdCents`, which applies a fixed demonstration exchange rate of 280 PKR per USD and enforces a fifty-cent minimum charge to satisfy Stripe's own minimum-amount constraint. The resulting session is created with metadata containing the `bookingId`, `guestId`, and `propertyId`, and the generated `sessionId` is persisted back onto the `Booking` document so that it can later be reconciled against Stripe's own record of the payment. Confirmation of a successful payment can arrive through either of two paths that both converge on the same helper, `markBookingStripePaid()`: `verifyCheckoutSession`, which the frontend calls after the guest is redirected back from Stripe's hosted checkout page, and the `/webhook` handler, which Stripe calls asynchronously and independently of the browser redirect. Both paths check that Stripe reports the session's `payment_status` as `"paid"` before calling `markBookingStripePaid()`, which sets the booking's `status` and `paymentStatus` fields to `confirmed` and its `paymentMethod` to `"stripe_test"`. A second endpoint, `confirmDemoPayment`, exists on the backend as a development and testing convenience that bypasses Stripe entirely, but it is not wired to any button or action in the deployed frontend; the Stripe test checkout flow is therefore the only payment path a real user of the application can currently trigger. Cancellation, handled by `cancelBooking`, simply sets the booking's `status` to `cancelled` without altering `paymentStatus`, which preserves an accurate historical record of whether a since-cancelled booking had actually been paid for.

### 3.11.5 Review and Sentiment Integration Implementation

Reviews are the mechanism through which IARS's sentiment analysis becomes visible to guests and owners, and `reviewController.createReview` is written to guarantee that a review can only be created under conditions that make it trustworthy. Before anything else, the controller confirms that the submitting guest holds a `confirmed` booking for the property in question, and that no review already exists for that same booking; this is enforced twice — once as an explicit application-level check inside the controller, and again as a unique index on the `Review` model's `booking` field, which acts as a database-level guarantee against a race condition producing duplicate reviews for the same booking. Only after both checks pass does the controller call `analyzeSentiment(text)`, the function exported from `services/sentimentService.js`, which sends the review's free-text content to the Python microservice's `/predict` endpoint and receives back a structured response containing a `sentiment` label, a `confidence` score, a list of `aspects`, per-aspect `aspectInsights`, and a short `summary`. These fields are mapped directly onto the corresponding fields of the new `Review` document, so the sentiment result is stored permanently alongside the review text rather than being recomputed on every subsequent read.

Immediately after the review is saved, the controller calls `propertySentimentStore.syncPropertySentiment(property)`, which re-aggregates every review associated with that property and writes the result into the property's own `sentimentSnapshot` field. This denormalisation is a deliberate performance decision: the property detail page, the search results list, and the candidate-scoring stage of the recommendation engine all need a property's aggregate sentiment picture frequently and cheaply, and recomputing it from the full `Review` collection on every one of those reads would be wasteful once a property accumulates a meaningful review history. By instead maintaining `sentimentSnapshot` as a materialised, eagerly updated summary that is only recalculated at the moment a new review is written, every other part of the system that needs a property's sentiment standing can read it directly off the `Property` document without touching the `Review` collection at all. The same `syncPropertySentiment` logic is reused by the `scripts/syncPropertySentiment.js` and `scripts/reanalyzeReviews.js` maintenance scripts, which allows the aggregate to be rebuilt in bulk if the underlying sentiment model or aggregation logic is ever revised, without requiring every review to be individually re-submitted through the API.

### 3.11.6 Offline Request Implementation

Not every prospective guest is comfortable completing an online card payment, and the offline request module exists to give such guests a form-based alternative route to inquire about a property. `offlineRequestController.createOfflineRequest` is deliberately placed behind `optionalProtect` rather than `protect`, which means both an authenticated guest and a completely anonymous visitor can submit a request; in the anonymous case, the resulting `OfflineRequest` document is stored with a `guest` field of `null` and relies instead on the phone number the visitor entered in the form. This design accommodates a realistic scenario in a property-booking context: a visitor may want to inquire about a listing before deciding whether the effort of registering an account is worthwhile.

The retrieval side of this workflow, `getGuestOfflineRequests`, has to reconcile that same scenario once the visitor eventually does create an account. It matches requests where the `guest` field equals the currently authenticated user's id, or, separately, where `guest` is `null` and the request's stored phone number matches the phone number on the authenticated user's profile. The first time a guest with a matching phone number logs in and views their offline requests, the controller performs an `updateMany` call that retroactively attaches their user id to any previously anonymous requests that match by phone, so that from that point forward those historical requests appear as a normal part of that guest's account rather than remaining orphaned anonymous records. On the owner side, `respondToOfflineRequest` allows an owner to set a `status` and `responseMessage` on a request directed at one of their properties, but only after verifying that the property referenced by the request actually belongs to the owner making the call — a check that prevents one owner from responding to, or even inferring the existence of, an offline request submitted against another owner's listing.

### 3.11.7 Recommendation Engine Implementation

The recommendation pipeline is orchestrated end-to-end by `searchController.getRecommendations`, which begins by running four largely independent data-gathering operations concurrently: `buildUserRecommendationProfile` (constructing a behavioural profile of the requesting guest, when one is authenticated), `getGlobalBookingCounts` (aggregate booking popularity across the platform), `buildCoOccurrenceMatrix` (the collaborative-filtering structure described in section 3.14.3), and a `Property.find({ status: "approved" })` query that gathers the full candidate pool of listings eligible for recommendation. Running these as parallel operations rather than sequentially was a deliberate performance choice, since none of them depends on the others' output and the naive sequential approach would otherwise add unnecessary latency to every recommendation request.

Once the candidate properties are retrieved, each one is enriched with its review statistics and sentiment summary before scoring begins, ensuring that every downstream scoring function — the Bayesian ranking described in section 3.14.1, the content-based similarity comparisons of 3.14.2, and the collaborative co-occurrence scoring of 3.14.3 — operates on a consistent, fully-populated candidate object rather than needing to fetch additional data mid-computation. The controller then calls `buildRecommendationMode`, a decision function that inspects the strength and quantity of signal available for the requesting guest — essentially, whether the guest has enough booking and viewing history to support a meaningful personalised profile — and chooses between two downstream builders accordingly: `buildStructuredRecommendations` for guests with sufficient interaction history, producing a personalised set of sections, or `buildColdStartRecommendations` for anonymous visitors or guests with too little history, which instead leans on popularity, Bayesian quality, and diversity heuristics to produce a still-useful result set without requiring any prior personal signal. In both cases, the final step is a call to `finalizePersonalizedRecommendations`, which enriches each recommended property's `matchReasons` — human-readable explanations of why a given property was surfaced, drawing on `recommendationEnrichment.js` — before the controller assembles the final response. That response is shaped as a set of named sections (each mapped in the frontend to a translated heading) plus a single flattened `data` array capped at twenty-four items via the `RECOMMENDATION_TOTAL` constant, giving the client a bounded, predictable payload size regardless of how many approved properties currently exist in the system.

### 3.11.8 Admin Module Implementation

Administrative oversight in IARS is split across three controllers, each responsible for one axis of platform governance. `listingModerationController` handles the approval workflow for newly submitted properties: `getPendingListings` returns every property still awaiting a decision, and for each one attaches an `imageSummary` that tallies how many of its images currently sit in the `verified`, `pending`, `suspicious`, and `rejected` states, giving the reviewing administrator an at-a-glance sense of how trustworthy a listing's photo evidence is before opening it in detail. `approveListing` enforces a hard gate on that trustworthiness: it calls `hasVerifiedImage(property.images)` and returns a 400 error if the listing does not have at least one image that has actually been verified, which prevents a property from going live with no verified visual evidence at all, regardless of how complete its textual description might be. `rejectListing` provides the corresponding negative outcome, moving the property out of the pending queue without ever exposing it to guests.

Image-level moderation is handled separately by `imageAuditController`, since a listing can be approved overall while individual images within it still need individual attention (for instance, an owner adding a new photo to an already-approved listing after the fact). `getImageAuditList` flattens every property's images into a single administrator-facing list spanning the whole platform, and, as part of building that list, refreshes the heuristic AI score for any image whose score is still in a pending state, ensuring the audit view reflects the current heuristic output rather than a stale value. `updateImageAudit` lets an administrator set an image's `verificationStatus` directly and, if desired, manually override its `aiScore` — human judgement is permitted to take precedence over the heuristic score in either direction — with one safeguard: setting the status to `rejected` always forces the stored `aiScore` to zero, so a rejected image can never be left carrying a score that would misleadingly suggest it had passed quality assessment.

The third axis, user governance, is handled by `userManagementController`. `getAllUsers` gives administrators visibility into the full user base, `updateUserVerification` lets an administrator mark a user's account as verified, and `updateUserRole` allows role changes between the platform's roles — but with two defensive checks built directly into the controller logic: an administrator is blocked from demoting their own account, and the system is blocked from demoting the last remaining administrator account on the platform. Both checks exist to prevent an administrative action from ever accidentally leaving the platform with zero administrator accounts able to manage it.

## 3.12 Sentiment Microservice Implementation

The sentiment microservice is implemented as a standalone FastAPI application, run under `uvicorn`, that is intentionally kept independent of the Node.js/Express server both as a process and as a codebase. At startup, the service loads a previously trained scikit-learn pipeline — a TF-IDF vectoriser paired with a logistic regression classifier — from disk using `joblib`, so that the comparatively expensive step of fitting the vectoriser's vocabulary and the classifier's weights happens once, offline, during a separate training run rather than on every request or every service restart. The model artifacts are trained on a labelled hotel-review dataset processed with `pandas`, where each review's raw text is transformed into a TF-IDF feature vector before being fit against the corresponding positive/negative/neutral sentiment labels; a dedicated training script performs this fitting step and persists the resulting vectoriser and classifier objects with `joblib` so that the FastAPI application can load them directly rather than repeating the training process at request time.

The service's single functional endpoint, `/predict`, accepts a piece of review text and returns a structured JSON payload containing a `sentiment` label, a `confidence` score, a set of detected `aspects` (aspect-level themes present in the review, such as cleanliness or location), `aspectInsights` describing the sentiment associated with each detected aspect, and a short human-readable `summary`. Internally, the prediction pipeline first passes the incoming text through the same TF-IDF vectoriser used during training and obtains the trained logistic regression classifier's predicted label and probability. That base classification is then checked against a rule-based negation-override layer, described in detail in section 3.14.4, which exists specifically to correct a known weakness of a bag-of-words-style TF-IDF representation: phrases such as "not clean" or "not good" can be scored as superficially positive by a classifier that has learned strong positive associations for words like "clean" or "good" without adequately weighting the preceding negation, and the rule-based layer intercepts these known negated-positive patterns and forces a negative classification with a high confidence value whenever they are detected, overriding the base classifier's output in that specific case. The final combined result — whichever of the base classifier's or the rule-based override's output prevails — is what is returned to the calling Express server through `sentimentService.js`, which the review controller then persists onto the corresponding `Review` document as described in section 3.11.5. Because the sentiment service is called synchronously from the Node.js backend but guarded by a timeout and a fallback path on the calling side, the microservice's availability is decoupled from the correctness of the rest of the review-creation workflow: a review can still be saved even if the sentiment service is briefly unreachable, with its sentiment fields simply left unpopulated until a later re-analysis pass (via `scripts/reanalyzeReviews.js`) can fill them in.

## 3.13 Frontend Implementation

### 3.13.1 Application Structure and Routing

The React client is bootstrapped in `main.jsx`, where a deliberate provider nesting order establishes the application's cross-cutting context before any route is rendered: `ThemeProvider` wraps `BrowserRouter`, which wraps `AuthProvider`, which wraps a `Toaster` (for transient notification messages) and finally the application's `Routes`. This ordering matters because both theme and authentication state need to be available to every routed page, and placing `BrowserRouter` between the two providers ensures that navigation triggered by either theme or authentication changes (for example, a redirect on logout) has access to the router. `AuthContext.jsx` is the central piece of client-side session state: it persists the JWT and the authenticated user object in `localStorage`, attempts to restore an existing session on mount by calling `GET /auth/me`, and exposes `login`, `register`, `logout`, and a `getDashboardPath` helper that maps a user's role to the correct landing route — `/guest/dashboard` for guests, `/owner/dashboard` for owners, and `/admin/dashboard` for administrators — which is used consistently across the login flow and any role-aware redirect logic rather than being recomputed ad hoc in individual components.

Route protection is layered through two composable components: `ProtectedRoute`, which acts purely as an authentication gate and redirects an unauthenticated visitor to the login page, and `RoleBasedRoute`, which wraps `ProtectedRoute` and additionally checks the authenticated user's role against a list of roles permitted for that route, redirecting to an appropriate fallback if the role does not match. Every guest, owner, and admin page in the application is reached through one of these guards, so a logged-in guest, for instance, cannot navigate directly to an admin route by manipulating the URL. Three distinct layout shells govern the visual chrome around routed pages: `PublicLayout`, which wraps a `Navbar` and `Footer` around unauthenticated, publicly browsable pages such as search and property details; `AuthShellLayout`, a minimal-header shell used specifically for the login and registration pages, where a full navigation bar would be redundant; and `DashboardLayout`, used by every guest, owner, and admin page, which renders a fixed sidebar whose navigation items are driven by a role-specific configuration object — Dashboard, My Bookings, and Offline Requests for guests; Dashboard, Properties, and Offline Requests for owners; and Dashboard, Moderate Listings, Manage Users, and Image Audit for administrators. Across the public, authentication, guest, owner, and admin route groups, the application comprises twenty-two page components in total, each mapped to one of these three layout shells according to its audience and authentication requirements.

### 3.13.2 Role-Based Dashboards

Because IARS serves three structurally different audiences through the same codebase, the dashboard experience for each role is composed from the same `DashboardLayout` shell but populated with entirely different content and navigation. The guest dashboard surfaces the guest's own bookings and offers quick access to their offline requests, giving a returning guest a single place to check the status of an in-progress booking or a pending offline inquiry without needing to search the platform again. The owner dashboard instead orients around the owner's property portfolio and the bookings made against it, with a dedicated Properties section for creating and editing listings via `PropertyForm.jsx` and a view of the offline requests submitted specifically against the owner's own properties. The admin dashboard is the most operationally dense of the three, giving direct navigation into the moderation queue (Moderate Listings), the platform-wide image audit list, and user management, reflecting the fact that an administrator's day-to-day interaction with the platform is almost entirely about governance rather than browsing or transacting.

This role-specific navigation configuration is what `DashboardLayout`'s sidebar reads from, rather than the sidebar itself containing any role-conditional branching logic; each role's page set and ordering is defined once, in one place, and the layout component simply renders whichever configuration corresponds to the currently authenticated user's role. Because `RoleBasedRoute` guards every route inside each of these dashboards, a guest who somehow navigates to an owner-only URL is redirected away rather than shown a broken or empty owner page, which keeps the three dashboard experiences cleanly separated even though they share the same underlying layout component and the same authentication context.

### 3.13.3 Booking and Review Flow Interfaces

The path from discovering a property to leaving a review after staying there spans several distinct page components, each corresponding to a specific stage of the workflow implemented on the backend. A guest first encounters `RecommendedProperties.jsx` or the search results view, both of which surface approved listings; `RecommendedProperties.jsx` in particular is written to handle two different response shapes coming back from the recommendation API, rendering a sectioned layout (mapping each section's `titleKey` through i18next to produce a translated heading) when the backend returns personalised or cold-start sections, and falling back to a flat grid when it does not, while also adjusting the hint text shown above the results depending on whether the visitor is anonymous, receiving a personalised result set, or receiving a cold-start result set. From a property's detail page, a guest proceeds into the booking flow, which surfaces the server-side availability and overlap validation described in section 3.11.4 as user-facing error messaging — a guest attempting to book already-booked dates is shown a message distinguishing whether they already hold a conflicting booking themselves or whether the conflict belongs to someone else, mirroring the `BOOKING_ALREADY_EXISTS` and `DATES_UNAVAILABLE` error codes returned by the API. Payment is completed through the Stripe test checkout redirect, after which the guest is returned to a confirmation view that reflects the booking's updated `confirmed` status once `verifyCheckoutSession` has run.

Once a booking reaches a confirmed state and its stay period has passed, the guest becomes eligible to leave a review, and the review submission form is gated by the same booking-ownership and no-existing-review rules enforced server-side, so the interface only offers the review action where it is actually valid to use it rather than surfacing a form that the backend would reject. On property detail pages, submitted reviews are displayed alongside their sentiment result and, in aggregate, the property's `sentimentSnapshot`, giving prospective guests a quick sense of how existing guests' feedback has trended before they commit to booking. On the owner side, `PropertyForm.jsx` — shared between the create-listing and edit-listing flows — submits its data as `FormData` rather than JSON, since it needs to carry both structured fields and binary image files in a single request; it serialises `availabilityCalendar` as a JSON string field within that form data, and, specifically when editing an existing listing, additionally includes a `retainedImageIds` field as a JSON-encoded array so the server can determine which existing images to keep alongside whatever new files are attached, exactly mirroring the `updateProperty` logic described in section 3.11.3.

### 3.13.4 Multilingual (i18n) and Right-to-Left Implementation

IARS is required to present its interface in English, Urdu, and Arabic, with English as the default language and Urdu and Arabic both rendered right-to-left, and this requirement is implemented through `i18next` and `react-i18next` backed by three separate JSON dictionary files, one per language, organised under nested domain-specific keys rather than as a single flat list of strings. Every piece of static interface text — button labels, navigation items, form labels, validation messages, section headings — is referenced in components through a translation key rather than being hard-coded, which is what makes it possible to add or adjust a language's wording without touching component code. A deliberate and important exception is carved out for user-generated content: property titles and descriptions, guest reviews, and personal fields such as names, emails, and phone numbers are never passed through the translation layer, since translating content that a real user actually typed would misrepresent what they wrote; these fields are rendered verbatim regardless of the interface's currently selected language.

The currently selected language is persisted in `localStorage` so that a returning visitor sees the interface in the language they last chose, and a `languageUtils` helper is responsible for applying the correct reading direction and language attribute to the document — setting `dir` to `rtl` for Urdu and Arabic and `ltr` for English, and setting `lang` accordingly on the root `<html>` element, which is what allows browser-level and assistive-technology behaviours (as well as CSS logical properties) to respond correctly to the active language. Because a right-to-left layout inverts the visual meaning of "left" and "right", components throughout the application avoid hard-coded directional classes in favour of direction-safe alternatives such as `text-start`/`text-end` and logical `start`/`end` spacing utilities rather than `text-left`/`text-right` or `ml-`/`mr-` utilities, alongside liberal use of `flex-wrap`, `w-full`, and responsive grid classes. This discipline is what keeps forms, property cards, tables, dashboard sidebars, the navigation bar, and the footer visually coherent regardless of which of the three supported languages and reading directions is active, rather than requiring a separate mirrored layout to be maintained for right-to-left languages.

### 3.13.5 Theming (Dark and Light Mode)

Alongside language, IARS supports a light and dark visual theme, implemented through `ThemeContext.jsx` and toggled from the interface via a dedicated `ThemeToggle` component. The context tracks the currently active theme, persists the user's choice in `localStorage` so it survives a page reload or a new session, and applies the corresponding theme class to the root `<html>` element, which allows Tailwind's dark-mode variant utilities used throughout the shadcn/ui-based component set to respond automatically without individual components needing their own theme-detection logic. Because the theme, language, and authentication contexts are all established at the top of the component tree in `main.jsx`, a change to any one of them — switching from light to dark mode, switching from English to Urdu, or logging in and out — takes effect consistently across every currently rendered page rather than requiring a full reload or per-page reinitialisation. This kept the theming implementation deliberately simple and scoped to exactly the two states the project requires, rather than expanding into a broader design-token system that would have gone beyond what the platform's UI actually needed.

## 3.14 Key Algorithms

Several parts of IARS depend on computation that goes beyond straightforward CRUD logic: ranking listings by trustworthy quality rather than raw average rating, judging how similar two properties are to one another, inferring a guest's preferences from their past behaviour without an explicit ratings matrix, and correcting for a specific, predictable failure mode of a bag-of-words sentiment classifier. The four subsections below present the core logic behind each of these, expressed as representative pseudocode of the reasoning implemented in the corresponding utility files rather than as literal file excerpts.

### 3.14.1 Bayesian Quality Ranking

Ranking properties purely by their raw average star rating rewards listings with very few reviews unfairly — a single five-star review produces a higher average than a listing with fifty reviews averaging 4.6 — so `bayesianRanking.js` instead computes a Bayesian-smoothed score that blends each property's own review history with a platform-wide prior. The prior assumes a baseline mean rating of 3.5 and is given a smoothing weight equivalent to four "phantom" reviews, meaning a property with very few real reviews has its score pulled substantially toward that neutral prior, while a property with a long, robust review history has its score dominated almost entirely by its actual reviews. On top of that Bayesian-smoothed base, the score is further penalised for low review credibility (very small review counts, which are inherently less trustworthy signals even after smoothing) and for a high proportion of negative sentiment among the property's reviews, so that a listing whose sentiment analysis skews negative does not rank as highly as its raw star average alone might suggest. Finally, a trust floor is applied through a `MIN_QUALITY_SCORE` constant of 0.28, ensuring that even a poorly-performing or extremely new listing retains some minimal baseline visibility rather than being scored at or near zero and effectively disappearing from ranked results.

```pseudocode
function bayesianQualityScore(property):
    PRIOR_MEAN = 3.5
    PRIOR_WEIGHT = 4
    MIN_QUALITY_SCORE = 0.28

    reviewCount = property.reviewStats.count
    averageRating = property.reviewStats.averageRating
    negativeShare = property.sentimentSnapshot.negativeRatio

    smoothedRating = (
        (PRIOR_WEIGHT * PRIOR_MEAN) + (reviewCount * averageRating)
    ) / (PRIOR_WEIGHT + reviewCount)

    credibilityPenalty = penaltyForLowReviewCount(reviewCount)
    sentimentPenalty = negativeShare * NEGATIVE_SENTIMENT_WEIGHT

    rawScore = normalize(smoothedRating) - credibilityPenalty - sentimentPenalty

    return max(rawScore, MIN_QUALITY_SCORE)
```

### 3.14.2 Content-Based Similarity Scoring

To recommend properties that resemble ones a guest has already shown interest in, `propertySimilarity.js` computes a weighted composite similarity score between a candidate property and a reference property (or a guest's aggregated preference profile) across four independent dimensions, each contributing a fixed share of the final score: whether the two properties are in the same city, contributing a weight of 0.32; how close their nightly prices are to one another, contributing 0.28; how much overlap exists between their amenity sets, measured as a Jaccard similarity and contributing 0.22; and how similar their aggregate guest sentiment profiles are, contributing the remaining 0.18. Weighting city match and price proximity most heavily reflects the practical reality that a guest browsing accommodation is usually anchored to a specific destination and budget range first, with amenity overlap and sentiment alignment acting as secondary refinements once those two harder constraints are already satisfied. Because each dimension's contribution is capped by its own weight, the four weights sum to exactly 1.0, keeping the final composite score on a consistent, easily-interpreted normalised scale regardless of how many of the four dimensions align strongly.

```pseudocode
function contentSimilarity(candidate, reference):
    citySim = candidate.city === reference.city ? 1 : 0
    priceSim = 1 - normalizedAbsoluteDifference(candidate.price, reference.price)
    amenitySim = jaccardSimilarity(candidate.amenities, reference.amenities)
    sentimentSim = 1 - normalizedAbsoluteDifference(
        candidate.sentimentSnapshot.positiveRatio,
        reference.sentimentSnapshot.positiveRatio
    )

    return (0.32 * citySim)
         + (0.28 * priceSim)
         + (0.22 * amenitySim)
         + (0.18 * sentimentSim)
```

### 3.14.3 Collaborative Filtering Co-Occurrence Scoring

Where content-based similarity reasons about the attributes of properties themselves, `collaborativeFiltering.js` reasons instead about patterns of behaviour across guests, without needing an explicit ratings matrix. It builds a co-occurrence matrix by scanning historical bookings and property views: every pair of properties that the same guest has booked contributes a full weight of 1 to that pair's entry in the matrix, while every pair of properties the same guest has merely viewed (without necessarily booking) contributes a smaller weight of 0.35, reflecting the intuition that a completed booking is a much stronger signal of genuine interest and satisfaction than a passing view. Once this matrix is built across all guests, scoring a specific candidate property for a specific guest is a matter of looking up every property already in that guest's own interaction set (their past bookings and views), summing the co-occurrence weight between the candidate and each of those known properties, and using that sum as the candidate's collaborative score — properties that have frequently co-occurred, across the platform's collective history, with properties this particular guest already engaged with end up scored more highly than properties with no such co-occurrence relationship at all.

```pseudocode
function buildCoOccurrenceMatrix(allBookings, allViews):
    matrix = {}

    for guestBookings in groupByGuest(allBookings):
        for (propertyA, propertyB) in allPairs(guestBookings):
            matrix[propertyA][propertyB] += 1
            matrix[propertyB][propertyA] += 1

    for guestViews in groupByGuest(allViews):
        for (propertyA, propertyB) in allPairs(guestViews):
            matrix[propertyA][propertyB] += 0.35
            matrix[propertyB][propertyA] += 0.35

    return matrix

function collaborativeScore(candidateProperty, guestInteractionSet, matrix):
    score = 0
    for knownProperty in guestInteractionSet:
        score += matrix[candidateProperty][knownProperty] || 0
    return score
```

### 3.14.4 Sentiment Rule-Based Negation Override

The sentiment microservice's primary classifier is a TF-IDF and logistic regression pipeline, which represents review text as a bag of weighted terms and is consequently prone to a well-known failure mode: a phrase like "not clean" or "not good" contains a strongly positive-associated word ("clean", "good") immediately preceded by a negation the vectoriser does not explicitly model as flipping that word's contribution. Left uncorrected, this can cause a review that is actually complaining about a property to be scored as positive simply because it contains vocabulary the classifier has learned to associate with positive reviews. To correct for this specific, predictable pattern, a rule-based override layer runs alongside the trained classifier: it pattern-matches the review text against a set of known negated-positive phrase patterns, and whenever one of those patterns is detected, it forces the final classification to negative with a confidence value of at least 0.88, regardless of what the base classifier's own probability output was. This override is intentionally narrow in scope — it targets a specific, well-understood blind spot of the bag-of-words model rather than attempting to re-implement general-purpose negation handling — and it is applied after the base classifier runs, so it acts strictly as a correcting layer on top of the trained model rather than as a replacement for it.

```pseudocode
NEGATED_POSITIVE_PATTERNS = [
    "not good", "not clean", "not friendly", "not comfortable",
    "not worth", "not great", "not nice"
]

function classifySentiment(reviewText, trainedModel):
    baseResult = trainedModel.predict(reviewText)

    for pattern in NEGATED_POSITIVE_PATTERNS:
        if reviewText.toLowerCase().includes(pattern):
            return {
                sentiment: "negative",
                confidence: max(0.88, baseResult.confidence)
            }

    return baseResult
```

## 3.15 Security Measures Implemented

Security in IARS was implemented as a series of targeted measures, each addressing a specific, identifiable risk rather than as a generic checklist applied uniformly without regard to what the platform actually needed to protect. Authentication risk is addressed first: sessions are stateless JSON Web Tokens signed with a configurable secret and a configurable expiry, which avoids the need for server-side session storage while still bounding how long a stolen or leaked token remains usable. Underneath that, credentials themselves are never stored in a recoverable form — passwords are hashed with bcrypt at ten salt rounds before being persisted, and the `User` schema additionally marks the password field as excluded from ordinary queries (`select: false`) and therefore from any JSON response the API returns, so that even a bug elsewhere in the codebase that accidentally serialises a full user document cannot leak a password hash to a client.

Authorisation is enforced structurally rather than left to individual controllers to remember: role-based middleware sits in front of every sensitive route, so that a request reaching a controller has already been confirmed to belong to an authenticated user of an appropriate role before any business logic executes, which removes an entire class of "forgot to check the role" bugs by making the check a routing-level concern instead of a per-controller one. Because client-side checks can always be bypassed by a sufficiently motivated or malicious client, the booking workflow deliberately re-validates ownership, property approval status, availability, and date-overlap conditions on the server even though the same checks already inform what the frontend displays and disables — the frontend's validation exists purely for user experience, while the server's validation is what actually protects data integrity.

Payment-specific risk is addressed at the configuration layer: the Stripe integration validates at startup that the configured secret key begins with the `sk_test_` prefix, which is a direct, low-effort safeguard against a misconfigured environment accidentally processing real charges against a live Stripe account during development or testing. Complementing that, incoming Stripe webhook events are verified against a signature computed with `STRIPE_WEBHOOK_SECRET`, so that the booking-confirmation logic triggered by a webhook call cannot be spoofed by an attacker simply posting a fabricated payload to the webhook URL. File-upload risk is constrained by the multer configuration underlying property image uploads, which limits both the number of files (a maximum of five) and the size of each file (five megabytes) and restricts accepted types to `jpg`, `png`, and `webp`, preventing arbitrarily large or arbitrarily typed files from being accepted through that endpoint. Separately, SHA-256 hashing of each uploaded image allows the system to detect duplicate uploads, which supports the integrity of the image-verification workflow by making it harder for a single image to be reused across multiple listings without that reuse being noticed. Finally, cross-origin access to the API is restricted to the configured `CLIENT_URL` with credentials enabled, rather than left open to any origin, which ensures that only the platform's own deployed frontend — not an arbitrary third-party site — can make authenticated, cookie- or credential-bearing requests against the API.
